# CrediBridge — Phase 5 Scoring Specification
### Explainable Micro-Credit Scoring Engine for Gig & Informal-Sector Workers
*Smart India Hackathon 2026 — Design Document (no code, no implementation)*

---

## 1. Executive Summary

CrediBridge Phase 5 introduces a **0–900, fully rule-based, deterministic credit score** built from four behavioral factors — Income Consistency, Payment Regularity, Earnings Trend, and Platform Tenure — plus a fifth, structurally separate module: **Score Confidence**, derived from Data Quality/Completeness.

The single most important design decision in this document is that **Data Quality is deliberately removed from the additive 900-point formula** and re-purposed as a confidence layer that caps and contextualizes the score rather than inflating it. The justification is given in Section 2.

Every number the score produces is generated by a closed-form statistical formula (median-based dispersion, Theil–Sen robust regression, Bayesian-style shrinkage, logarithmic saturation curves) — never a trained/opaque model. Every explanation string is a template bound to a named intermediate variable, so every sentence shown to a worker or a judge can be traced back to an exact calculation.

---

## 2. Recommended Weights — and Why They Changed

### 2.1 The core problem with the original 5-factor proposal

The brief itself flags the tension: *"Data quality should primarily represent confidence in the score, not directly claim that a worker is financially reliable."* If Data Quality is nonetheless given a 10% **additive** weight inside the 900-point formula, that instruction is violated by construction — a worker who simply uploads more CSV rows, with **identical financial behavior**, would receive a materially higher score than a worker who uploaded less. That is a measurement-reliability signal, not a creditworthiness signal, and mixing the two:

- rewards data *volume* over data *behavior* (gameable, and philosophically wrong for a "explainable, defensible" score),
- makes the score harder to justify to a judge asking "why did uploading more rows make this person more creditworthy?",
- is a well-known critique of naive alternative-data scoring systems.

### 2.2 Recommendation

Keep **four** behavioral factors inside the additive 900-point score, re-normalized from the original proposal so their *relative* proportions are preserved:

| Factor | Original weight | Re-normalized weight | Points (of 900) |
|---|---|---|---|
| Income Consistency | 30% | **33%** | 297 |
| Payment Regularity | 25% | **28%** | 252 |
| Earnings Trend | 20% | **22%** | 198 |
| Platform Tenure | 15% | **17%** | 153 |
| **Total** | 90%* | **100%** | **900** |

*(\*the original 10% for Data Quality is removed from the sum.)*

Data Quality/Completeness becomes **Score Confidence** (Section 7) — a separate 0–100 metric with Low/Medium/High tiers that (a) caps the maximum displayable score, (b) is shown as its own badge next to the score, and (c) can trigger an "Insufficient Data" state instead of a number. This is explained fully in Section 7 and defended in Section 12 (Q1–Q3).

This re-weighting satisfies the brief's own permission: *"You may challenge these weights if you have a strong technical/reasoned justification."*

### 2.3 A cross-cutting design principle

Two rules apply to **every** factor below, and are worth stating once, up front:

1. **Scale-invariance.** No factor ever uses the *absolute rupee value* of a worker's earnings. Only ratios, percentages, coefficients of variation, and log-scaled counts are used. A worker earning ₹8,000/month with perfect discipline scores identically (on Income Consistency, Payment Regularity, and Trend) to a worker earning ₹80,000/month with the same discipline. This is a deliberate fairness safeguard (see Section 11).
2. **Self-referential baselines.** Every worker is compared only to **their own** history — never ranked against other workers, occupations, or platforms. This avoids penalizing occupations or regions with structurally different income patterns.

## 3. Exact Aggregate Formula

**Step 1 — Per-factor sub-scores.** Each of the four factors produces a sub-score in the range 0–100 (formulas in Section 4).

**Step 2 — Weight redistribution.** If a factor cannot be computed at all (zero usable data — see Section 5), it is **excluded**, and the remaining factors' weights are redistributed proportionally so they still sum to 100%:

```
w_i' = w_i / Σ(w_j for j in included factors) × 100
```

**Step 3 — Raw score.**

```
RawScore₉₀₀ = Σ over included factors [ (SubScore_i / 100) × (w_i' / 100) × 900 ]
```

**Step 4 — Minimum scoring threshold.** If fewer than 2 of the 4 factors are includable, no numeric score is produced at all — the platform shows an explicit **"Insufficient Data"** state (Section 5).

**Step 5 — Confidence cap.**

```
DisplayedScore = round( min( RawScore₉₀₀ , ConfidenceCap ) )
```

where `ConfidenceCap` is 900 (High confidence), 820 (Medium), or 650 (Low) — see Section 7.

This five-step chain is the entire scoring pipeline. Nothing else influences the number.

## 4. Factor-by-Factor Scoring Rules

### 4.1 Income Consistency — 33% (max 297 pts)

**Definition.** How stable a worker's recorded monthly earnings are, using a dispersion measure that is robust to single-month outliers, so that ordinary gig-income volatility is not mistaken for financial instability.

**Why relevant.** Lenders need to estimate whether a worker can reliably set aside funds for repayment. Predictability matters more than absolute income level for this purpose.

**Statistical method — Robust Coefficient of Variation.** Standard CV (`stdev/mean`) is fragile: one unusually large or small month (a bonus, a slow week) swings both the mean and the standard deviation. Instead:

```
median_e   = median(monthly earnings)
deviations = [ |e_t − median_e| for each month t ]
MAD        = median(deviations)                 # Median Absolute Deviation
RobustCV   = MAD / median_e
```

MAD is unaffected by a single extreme month because it uses the *median* of deviations, not the mean — this directly answers the brief's requirement to not conflate normal gig variance with instability while still catching genuinely erratic earners (where deviations are large across *many* months, not just one).

**Normalization — piecewise-linear interpolation** between fixed breakpoints (transparent, no hidden thresholds):

| RobustCV | 0.00 | 0.15 | 0.30 | 0.50 | 0.80 | 1.20+ |
|---|---|---|---|---|---|---|
| Raw Score | 100 | 90 | 75 | 55 | 30 | 10 (floor) |

Linear interpolation between adjacent points; below 0 clamp to 100, above 1.20 clamp to the floor of 10 (never 0 — a nonzero floor avoids a single bad stretch producing a mathematically-final "zero forever" signal, while still allowing the score to fall very low over a sustained pattern).

**Insufficient-data shrinkage.** With few months of data, RobustCV is statistically noisy. Apply Bayesian-style shrinkage toward a neutral prior:

```
FinalSubScore = (n × RawScore + k × 70) / (n + k)      where k = 3, n = months of earnings data
```

The prior (70) represents "no strong evidence either way" — mildly above the midpoint, but well below what real positive evidence produces, so it can't be gamed by simply having a short history. The shrinkage weight (`k/(n+k)`) fades smoothly as more months arrive: 33% of the score at n=6, 20% at n=12 — **no cliff-edge jump**, satisfying the "avoid arbitrary jumps" principle everywhere, not just for tenure.

**Inputs required:** monthly earnings totals with associated calendar months.

**Min/max contribution:** 0.10 × 297 ≈ 3 pts (floor case, heavily shrunk) to 297 pts.

**Positive conditions:** low RobustCV; earnings cluster tightly around the median across most months.

**Negative conditions:** high RobustCV sustained across *many* months (a single spike or dip barely moves MAD); frequent very-low or zero-income months.

**Missing data (0 months of earnings):** factor **excluded**, weight redistributed (Section 5).

**Insufficient history (1 month):** cannot compute any deviation — treated as excluded (n=1 is mathematically degenerate for MAD). From n=2 upward, computed with shrinkage as above.

**Worked Example A (fairly stable worker, 6 months):** Earnings ₹17,800 / 18,000 / 18,900 / 19,200 / 19,500 / 20,100.
`median = 19,050`, `MAD = 750`, `RobustCV = 750/19,050 = 0.039`.
Interpolating between (0.00,100) and (0.15,90): RawScore ≈ `100 − (0.039/0.15)×10 ≈ 97.4`.
Shrinkage (n=6, k=3): `(6×97.4 + 3×70)/9 ≈ 88.3`. **Contribution ≈ 262 / 297 pts.**

**Worked Example B (spiky/seasonal worker, 6 months):** Earnings ₹8,000 / 9,000 / 10,000 / 12,000 / 25,000 / 27,000 (two festival-season months).
`median = 11,000`, `MAD = 2,500`, `RobustCV = 0.227`.
Interpolating between (0.15,90) and (0.30,75): RawScore ≈ `90 − 0.513×15 ≈ 82.3`.
Shrinkage: `(6×82.3 + 3×70)/9 ≈ 78.2`. **Contribution ≈ 232 / 297 pts.**
Note: despite two months earning 2–3× the norm, the score stays in a healthy range — the median-based method absorbs seasonal spikes gracefully.

### 4.2 Payment Regularity — 28% (max 252 pts)

**Definition.** How reliably a worker meets due dates on recorded utility/rent payments.

**Why relevant.** Bill-payment punctuality is one of the strongest behavioral proxies for repayment discipline available without a formal credit file (the same principle behind alternative-data scoring pilots like utility-based credit-building programs).

**Formula.** For every payment record with both a due date and a paid date, compute `delta = paid_date − due_date` (days; positive = late) and assign points:

| Category | Condition | Points |
|---|---|---|
| On-time / early | delta ≤ 0 | 100 |
| Grace-period late | 0 < delta ≤ 5 | 85 |
| Late | 5 < delta ≤ 15 | 50 |
| Severely late | delta > 15 | 15 |
| Unpaid (explicit flag) | marked unpaid | 0 |

```
RawAverage = mean(points across all usable records)
```

**Insufficient-data shrinkage** (same mechanism as 4.1, tuned for payment records):

```
FinalSubScore = (n × RawAverage + k × 70) / (n + k)     where k = 5, n = usable payment records
```

k=5 is larger than the k=3 used for Income Consistency because a single payment record carries less statistical information than a single month of earnings (one late fee could be a one-off event, e.g. a bank holiday). The shrinkage naturally makes one bad record much less punishing, and one perfect record much less rewarding, than it would look unshrunk — both cases the brief explicitly worries about.

**Normalization:** already 0–100 by construction (weighted average of bounded points), no further transform needed.

**Min/max contribution:** ≈ 0 to 252 pts (never truly 0 unless every record scores 0 *and* n is large enough to overcome the k=5 prior pull).

**Positive conditions:** high proportion on-time/early; few or no severely-late/unpaid records.

**Negative conditions:** recurring late or severely-late payments across many records (not just one).

**Treatment of missing payment dates:** a record missing its `paid_date` (partial record) is **excluded from the calculation entirely** — it is neither counted as on-time nor as late. It is separately tracked as a "data-validity" issue for the Confidence module (Section 7).

**Treatment of records with no match at all (a month simply has no payment entry):** explicitly **not** treated as late or missed. Per the brief's instruction, *absence of a record is not evidence of non-payment* — it is evidence of nothing, and is handled purely as reduced `n` (which increases shrinkage toward the neutral prior, i.e., reduces confidence, not the raw behavioral read).

**Missing data (0 usable records):** factor **excluded**, weight redistributed — the system deliberately does **not** silently fall back to the shrinkage prior for zero records, because doing so would let a completely-undocumented worker show a plausible-looking "70" for a factor that has no evidence behind it at all. Exclusion + redistribution is more honest.

**Insufficient history (1–4 records):** included, heavily shrunk (k=5 dominates at this range).

**Worked Example A (well-documented, mostly on-time; 20 records):** 18 on-time, 2 grace-late.
`RawAverage = (18×100 + 2×85)/20 = 98.5`.
Shrinkage: `(20×98.5 + 5×70)/25 = 92.8`. **Contribution ≈ 234 / 252 pts.**

**Worked Example B (irregular payer; 8 records):** 3 on-time, 2 grace-late, 2 late, 1 severely late.
`RawAverage = (300+170+100+15)/8 = 73.1`.
Shrinkage: `(8×73.1 + 5×70)/13 = 71.9`. **Contribution ≈ 181 / 252 pts.**

### 4.3 Earnings Trend — 22% (max 198 pts)

**Definition.** The direction and rate of change of earnings over time, computed with a robust, outlier-resistant estimator, and — when enough history exists — corrected for seasonal cycles so seasonal dips are not misread as decline.

**Why relevant.** A rising or flat trend signals stable-or-growing repayment capacity; a genuine sustained decline is a real risk signal that Income Consistency (which only measures dispersion, not direction) cannot catch on its own.

**Method — Theil–Sen estimator** (median of all pairwise slopes), not ordinary least-squares regression:

```
for every pair of months (i, j), i < j:
    slope_ij = (earnings_j − earnings_i) / (j − i)
TrendSlope = median(all slope_ij)
NormalizedSlope(%/month) = 100 × TrendSlope / median(earnings)
```

Theil–Sen is preferred over OLS because it has a breakdown point of ~29% — up to roughly a third of the months can be extreme outliers (a bonus month, a festival spike) without corrupting the slope estimate, whereas OLS is dragged by even one such month. It is still fully deterministic and explainable as "the typical month-over-month growth rate."

**Seasonality handling (only when ≥12 months of data exist).** Using the classical *ratio-to-moving-average* decomposition (no ML required):

```
for each calendar month m:
    seasonal_index_m = average( earnings_t / centered_moving_average_t )  over all t in month m
Deseasonalized_t = earnings_t / seasonal_index_{month(t)}
```

Theil–Sen is then run on the **deseasonalized** series instead of the raw one. With fewer than 12 months, a reliable seasonal index cannot be estimated (you need at least one full cycle, ideally two) — the system **explicitly does not attempt it** and instead flags "seasonal adjustment not applied — insufficient history for a full annual cycle" in the explanation. This honesty is a deliberate design choice: pretending to detect seasonality from 3–4 months of data would be statistically indefensible in front of judges.

**Normalization — piecewise-linear bands** on `NormalizedSlope`:

| %/month | ≤ −8% | −3% | −1% | 0% | +3%+ |
|---|---|---|---|---|---|
| Raw Score | 10 (floor) | 35 | 60 | 70 | 100 |

Linear interpolation between points; note flat/stable (0%) already scores 70 — a non-growing but non-declining worker is not penalized.

**Insufficient-data shrinkage:** `FinalSubScore = (n×RawScore + k×70)/(n+k)`, k = 3, n = months of earnings history (same mechanism as 4.1).

**Inputs required:** the same monthly earnings series used in 4.1, ordered chronologically.

**Min/max contribution:** ≈ 2 pts (heavily shrunk, near-floor) to 198 pts.

**Positive conditions:** stable-to-rising deseasonalized trend.

**Negative conditions:** sustained decline that survives Theil–Sen's outlier resistance (i.e., not explained away by one bad month).

**Missing data (0–1 months):** a slope requires at least two points; with 0 or 1 month, factor **excluded**, weight redistributed.

**Insufficient history (2–5 months):** included with a single or small number of pairwise slopes, heavily shrunk toward neutral; seasonal adjustment never attempted below 12 months.

**Worked Example A (steady growth, 6 months):** ₹15,000 / 15,300 / 15,600 / 16,100 / 16,400 / 16,700 → Theil–Sen slope ≈ ₹320/month → `NormalizedSlope ≈ 2.0%/month` → RawScore = `70 + (2.0/3)×30 ≈ 90`. Shrinkage (n=6,k=3): `(6×90+3×70)/9 ≈ 83.3`. **Contribution ≈ 165 / 198 pts.**

**Worked Example B (one-off spike, 4 months):** ₹10,000 / 10,200 / 18,000 (festival month) / 10,400. All six pairwise slopes: 200, 4,000, 133, 7,800, 100, −7,600 → median = **166.5**. `NormalizedSlope = 166.5/10,100 ≈ 1.65%/month` → RawScore = `70 + (1.65/3)×30 ≈ 86.5`. Shrinkage (n=4,k=3): `(4×86.5+3×70)/7 ≈ 79.4`. **Contribution ≈ 157 / 198 pts.**
Note how the *median* of pairwise slopes (not a mean or OLS fit) keeps the single spike from dominating the read — the estimator itself absorbs the outlier before any explicit seasonality correction is even applied.

### 4.4 Platform Tenure — 17% (max 153 pts)

**Definition.** Months elapsed since the worker's first recorded activity on the platform.

**Why relevant.** Tenure is a weak-but-real proxy for stability and gives more opportunity to observe behavior — but it is the *least* directly causal of the four factors, which is why it carries the lowest weight.

**Scoring curve — logarithmic saturation** (smooth, no arbitrary jumps):

```
TenureSubScore = 100 × ln(1 + months) / ln(1 + CAP)     where CAP = 36 months, capped at 100
```

**Should tenure be capped? Yes.** Beyond ~3 years, additional tenure adds negligible extra predictive value in a gig economy where platforms, policies, and a worker's own financial circumstances change materially within that window — an uncapped curve would let tenure alone dominate a score that should be led by *recent* behavior (Income Consistency + Payment Regularity together already carry 61% of the score).

Curve values for reference: 1 month → 19.2; 6 months → 53.9; 12 months → 71.0; 24 months → 89.1; 36+ months → 100.

**Inputs required:** platform join date (or first-activity date if join date unavailable).

**Min/max contribution:** 0 pts (day 0) to 153 pts.

**Positive conditions:** longer continuous tenure.

**Negative / neutral conditions:** very new accounts — this is not treated as negative, only as low-information; a brand-new worker scores near 0 on *this factor alone*, not on the overall score, and their other three factors are unaffected.

**Missing data (no join date at all):** factor **excluded**, weight redistributed.

**Tenure = 0 (joined today):** this is a **valid, exact data point**, not missing data — it is scored 0 on this factor deliberately (no track record yet exists), not excluded. Unlike the other three factors, tenure requires no shrinkage: it is an exact fact, not a noisy statistical estimate.

**Worked Example A:** 18 months → `100×ln(19)/ln(37) ≈ 81.5`. **Contribution ≈ 125 / 153 pts.**

**Worked Example B:** 2 months (new worker) → `100×ln(3)/ln(37) ≈ 30.4`. **Contribution ≈ 47 / 153 pts** — still meaningfully above zero for simply being present, reflecting the gradual curve rather than a threshold.

## 5. Missing-Data Rules (Unified Policy)

The brief asks explicitly whether the system should redistribute weights, reduce confidence, cap the maximum score, or display "insufficient data." **The recommended answer is all four, applied at different severities:**

| Situation | Rule applied |
|---|---|
| A factor has **zero** usable data points (or below the mathematical minimum needed to compute anything — e.g. 1 month for Income Consistency, 0–1 months for Trend) | **Exclude** the factor; **redistribute** its weight proportionally across the remaining included factors (Section 3, Step 2). |
| A factor has **some but limited** data | **Include** it, but **shrink** its raw sub-score toward a neutral prior (70) using the factor-specific Bayesian formula (Sections 4.1–4.3). Shrinkage fades smoothly as more data arrives — never a hard cutoff. |
| Fewer than **2 of the 4** factors are includable at all | Do not compute a numeric score. Display an explicit **"Insufficient Data"** state (grey/neutral UI, not a red/negative one — this must not read as a penalty to a brand-new worker). |
| Confidence tier is Low or Medium (Section 7) | **Cap** the maximum displayable score (650 or 820 respectively), regardless of the raw computed value. |
| A profile is incomplete (fields blank) or has missing `paid_date`s | Does **not** zero out any factor directly — instead it lowers the **Confidence Score** (Section 7), which can trigger the cap above. |

This layered approach means a thin-file worker is never punished by having a factor forced to zero, but is also never allowed to present a thin file as equivalent in *certainty* to a well-documented one.

## 6. Seasonality Handling

Handled at its natural home — inside Earnings Trend (Section 4.3) — via two complementary, non-ML mechanisms:

1. **Robust estimation by default.** The Theil–Sen median-of-pairwise-slopes estimator already resists being fooled by any single seasonal spike or dip, even with no explicit seasonal model (demonstrated in Worked Example B, Section 4.3).
2. **Explicit deseasonalization once enough history exists (≥12 months).** Classical ratio-to-moving-average decomposition computes a seasonal index per calendar month from the worker's *own* history and removes it before computing the trend slope — again, no ML, no black box, and fully re-derivable by hand.

Crucially, **Income Consistency intentionally does not attempt to detect or remove seasonality.** It measures raw dispersion only. A seasonal worker will therefore naturally read as "moderate" (not "poor") on Income Consistency, which is fair — the *direction* correction belongs to Trend, not Consistency, and Payment Regularity is unaffected by earnings seasonality altogether, so a punctual seasonal worker's bill-paying record is scored on its own merits.

Below 12 months, no seasonal claim is made at all — the explanation text says so directly (Section 9), rather than guessing.

## 7. Score-Confidence Methodology

**Concept.** Confidence answers *"how much do we trust this number?"* — a completely different question from *"is this worker financially reliable?"* A worker with two months of flawless behavior should show a **strong underlying signal but Low confidence**; the system must never blur these into one number.

**Confidence Score (0–100):**

| Component | Formula | Weight |
|---|---|---|
| Earnings coverage | `min(months_of_earnings / 6, 1) × 100` | 30% |
| Payment coverage | `min(payment_records / 10, 1) × 100` | 30% |
| Profile completeness | `filled_required_fields / total_required_fields × 100` | 20% |
| Source diversity | `min(distinct_income/payment_sources / 3, 1) × 100` | 10% |
| Data validity | `records_passing_sanity_checks / total_records × 100` (no negative amounts, valid dates, no duplicates) | 10% |

```
ConfidenceScore = 0.30×Earnings + 0.30×Payment + 0.20×Profile + 0.10×Diversity + 0.10×Validity
```

**Tiers and score caps:**

| ConfidenceScore | Tier | Max displayable score |
|---|---|---|
| ≥ 75 | **High** | 900 (no cap) |
| 40–74 | **Medium** | 820 |
| < 40 | **Low** | 650 |
| — | *(and, separately)* fewer than 2 factors includable → **Insufficient Data**, no score shown at all |

**UI communication.** The score and confidence are **always shown as two separate elements**, never merged: e.g. *"Score: 640 (Moderate) — Confidence: Medium."* The interface should never render a bare number without its confidence badge next to it, and should message thin-file cases constructively, e.g.: *"This score is based on 4 months of data. As you add more records, your confidence — and the precision of your score — will improve."*

## 8. Score Bands

Deliberately **not** copied from CIBIL's terminology, and framed constructively for an informal-sector audience building a track record for the first time:

| Band | Range | Rationale |
|---|---|---|
| **Very Strong** | 750–900 | Deep, consistent, well-documented behavioral evidence across all four factors. |
| **Strong** | 650–749 | Solid behavior with at most minor weaknesses in one factor. |
| **Moderate** | 500–649 | Reasonable behavior but with a real weak spot (e.g. late payments, or a still-short history pulling scores down via shrinkage). |
| **Emerging** | 350–499 | Meaningful gaps in consistency or payment discipline, or a still-thin file — "emerging" rather than "poor" because for a first-time formal-credit applicant this is a starting point, not a verdict. |
| **Building History** | 0–349 | Very limited or weak evidence; deliberately named to describe a *process* the worker is in, not a fixed label. |
| **Insufficient Data** | *(no number shown)* | Fewer than 2 factors computable at all — see Section 5. |

The Low-confidence cap (650) means a thin file can reach at most "Moderate" — it structurally cannot present as "Strong" or "Very Strong" until more evidence exists, regardless of how good the limited evidence looks.

## 9. Explainability Methodology

Every sentence shown to a worker or judge is a **fixed template with variables sourced directly from the computation**, never free-text generation. Two additional rules keep this honest:

- **Templates show the worker's raw observed statistics** (e.g. actual on-time %), while the **score itself may be statistically shrunk** for a short history — and the explanation says so explicitly, so a worker never sees a number that silently disagrees with their plain-English summary.
- Every explanation names the sample size (`n`) it's based on.

Example templates (variables in `{braces}` are computed, not generated):

- *"Your earnings varied by about {RobustCV×100}% relative to your typical month over the last {n} months, which is considered {band_label}."*
- *"{on_time_pct}% of your {n} recorded payments were made on or before the due date. {If shrunk: 'A small statistical adjustment was applied because {n} records is not yet a long history.'}"*
- *"Your earnings show a {trend_direction} trend of about {NormalizedSlope}% per month over {n} months. {If <12 months: 'Seasonal adjustment was not applied because at least 12 months of history is needed.'}"*
- *"Your platform tenure is {months} months."*
- *"Only {n} months of financial data are available, so confidence in this score is {tier}."*

## 10. Synthetic-Worker Expected Outcomes (Qualitative)

*(No exact numbers invented, per the brief — directional expectations only, using the formulas above.)*

**`stable_worker`** — low RobustCV → Income Consistency high; mostly on-time payments → Payment Regularity high; flat-to-mild-positive slope → Trend high; assume moderate-to-long tenure → Tenure medium-high; rich dataset → **High confidence**. Expected band: **Strong to Very Strong**.

**`seasonal_worker`** — RobustCV moderate (seasonal swings raise dispersion somewhat even with the MAD-based method) → Income Consistency moderate; punctual bill payment is a behavior independent of earnings seasonality → Payment Regularity can still be high; if ≥12 months of data exist, deseasonalized Trend should read stable-to-positive, **not** declining; with a full year of data, confidence can be High. **Key qualitative target: this preset must land in Moderate-to-Strong, not Emerging/Building History, specifically because seasonality alone should never be the deciding factor.**

**`irregular_worker`** — high RobustCV sustained across many months → Income Consistency low; a real pattern of late/severely-late payments (not just one) → Payment Regularity meaningfully lower, though shrinkage prevents a single bad record from being catastrophic; noisy or declining Trend, softened somewhat by Theil–Sen's outlier resistance but still reading lower than the other presets; confidence can still be Medium-to-High if enough records exist (irregularity is a behavior signal, not a data-availability problem). Expected band: **Emerging to Moderate** — genuinely lower, as it should be, since the floors in each factor exist to avoid numerical degeneracy on a single bad month, not to shield a *sustained* pattern of poor behavior from a low score.

## 11. Fairness / Bias Analysis

| Risk | Mitigation already built into the design |
|---|---|
| **Platform differences** (some platforms structurally pay more/less regularly) | The score is scale-invariant (Section 2.3) — CV, %-growth, on-time %, and log-tenure never use absolute ₹ amounts. |
| **Occupation differences** (delivery vs. domestic work vs. tailoring have different natural cadences) | Every factor is computed relative to the worker's **own** history, never against a peer population or occupation benchmark. |
| **Geographic differences** (rural digital-record gaps) | Handled by the Confidence layer (thin file → Low confidence + score cap) rather than a low raw score; manual/CSV entry is treated identically to platform-linked data. |
| **Seasonal workers** | Addressed explicitly in Trend (Section 4.3/6) via deseasonalization once enough history exists, and Income Consistency does not try to detect seasonality at all, avoiding double-penalization. |
| **Workers with limited financial history** | Redistribution + shrinkage (Section 5) instead of zero-fill; confidence cap instead of a fabricated high score. |
| **Workers who can't provide certain data** (e.g. cash-based rent, no bank link) | Handled by the same redistribution mechanism; explicitly disclosed as a known blind spot below. |
| **Income level** | Never a direct input to any factor — see scale-invariance principle. |
| **Data availability generally** | Uniform confidence-cap logic across every factor. |

**Limitations to disclose honestly to SIH judges:**

1. This is a **synthetic-data prototype** — the score has not been statistically validated against real repayment/default outcomes. The weights are reasoned, not empirically fitted.
2. Deseasonalization is impossible with less than 12 months of history — a genuine limitation for new users that the system discloses rather than hides.
3. Manually entered/self-reported data is not independently verified in this phase; fraud/gaming resistance is out of scope for Phase 5.
4. A production system would need real repayment-outcome data and a calibration step (e.g., checking predicted bands against actual default rates) before the weights could be considered validated rather than reasoned defaults.
5. Fairness claims here are architectural (scale-invariance, self-referential baselines), not yet empirically audited across a large, diverse real population.
6. No adverse-action/appeal workflow is designed in this phase; a real deployment handling credit decisions would need one.

## 12. Judge-Defense Answers

**1. Why these factors?** They map directly to the three things a micro-lender actually needs to know without a credit bureau file: can this person repay predictably (Income Consistency, Trend), do they honor obligations on time (Payment Regularity), and is there a track record to observe at all (Tenure) — plus a separate honesty layer (Confidence) about how much evidence backs the answer.

**2. Why these weights?** Behavioral, near-term evidence (Income Consistency + Payment Regularity = 61%) is weighted above trend and tenure because it is the most direct and most recent signal of repayment capacity; tenure is weakest because it is only a proxy, not a behavior. The exact re-normalization from the original proposal is shown and justified in Section 2.

**3. Why not use CIBIL?** CIBIL requires formal credit history that, by definition, gig and informal workers largely don't have. CrediBridge is built entirely from data these workers *already generate* (gig earnings, utility/rent payments) and uses different band names deliberately so it is never confused with, or misrepresented as, a bureau score.

**4. Why not machine learning?** With no real historical default-outcome data to train or validate against, an ML model here would be uncalibrated and unauditable — the opposite of "explainable." Every formula in this document (median/MAD, Theil–Sen, log curves, Bayesian shrinkage) is closed-form, reproducible by hand, and directly explainable to the worker it affects.

**5. How is income volatility handled?** Via a median/MAD-based dispersion measure (Section 4.1) that resists single-month outliers, combined with shrinkage so short histories aren't over-penalized for natural noise.

**6. How are seasonal workers handled?** Robust slope estimation by default, plus explicit calendar-based deseasonalization once ≥12 months of history exist (Sections 4.3, 6) — and Income Consistency deliberately does not attempt seasonal detection, so seasonality is corrected once, in the right place.

**7. How is missing data prevented from becoming a penalty?** Weight redistribution for fully-missing factors, Bayesian shrinkage (not zero-fill) for sparse-but-present factors, and a confidence cap rather than a fabricated low score (Section 5).

**8. How is the score explainable?** Every displayed sentence is a template bound to a named computed variable (Section 9) — there is no generative or opaque step between the math and the explanation text.

**9. How is this different from just ranking income?** Absolute income is never used anywhere in the formula (Section 2.3) — the score measures *behavior relative to the worker's own history*, not income magnitude.

**10. How could this be validated with real lenders?** By tracking actual repayment outcomes for a cohort scored by this system, then checking calibration (do "Very Strong" workers actually default less than "Emerging" workers) and adjusting weights/breakpoints using that outcome data — the formula structure is built to accept re-tuned constants without an architecture change.

**11. Current limitations of a synthetic-data prototype?** See Section 11 — no outcome validation yet, no fraud-resistance testing, no large-scale fairness audit.

**12. How would you monitor fairness after deployment?** Periodically comparing score distributions and band placement across occupation, region, platform, and gender subgroups, watching specifically for the risks listed in Section 11, alongside a human-reviewable appeal path for any adverse credit decision.

## 13. Limitations

*(Consolidated from Sections 6, 11, and 12 for a single honest summary — no new content beyond what's stated above.)* This is a synthetic, unvalidated, non-ML, single-phase prototype: weights and breakpoints are reasoned rather than statistically fit; seasonality correction requires 12+ months not yet available for new users; self-reported data is unverified; fairness is architectural, not yet empirically audited; no appeal workflow exists yet.

## 14. Complete Worked Example — "Rina," 9 Months of Data

**Inputs:** Earnings (₹, 9 months): 14,000 / 13,500 / 15,200 / 14,800 / 16,000 / 15,500 / 16,800 / 15,900 / 17,200. Payments: 14 records — 11 on-time, 2 grace-late, 1 late. Tenure: 9 months. Profile: fully complete. Sources: 2 (gig platform + manual rent entry).

| Factor | Raw calculation | Raw score | Shrunk (n, k) | Contribution |
|---|---|---|---|---|
| Income Consistency | median=15,500; MAD=700; RobustCV=0.045 | 97.0 | (9,3) → 90.2 | **268 / 297** |
| Payment Regularity | (11×100+2×85+1×50)/14 = 94.3 | 94.3 | (14,5) → 87.9 | **222 / 252** |
| Earnings Trend | Theil–Sen slope ≈ +₹380/mo → 2.45%/mo (method as in 4.3; <12mo so no deseasonalization) | 94.5 | (9,3) → 88.4 | **175 / 198** |
| Platform Tenure | 100×ln(10)/ln(37) | 63.8 | *(no shrinkage — exact fact)* | **98 / 153** |

**RawScore₉₀₀ = 268 + 222 + 175 + 98 = 762**

**Confidence:** Earnings coverage = min(9/6,1)×100 = 100; Payment coverage = min(14/10,1)×100 = 100; Profile = 100; Diversity = min(2/3,1)×100 = 66.7; Validity = 100.
`ConfidenceScore = 0.30(100)+0.30(100)+0.20(100)+0.10(66.7)+0.10(100) = 96.7` → **High** → cap = 900 (no cap applied).

**Final: Displayed Score = 762 → Band: Very Strong. Confidence: High.**

Generated explanations:
- *"Your earnings varied by about 5% relative to your typical month across 9 months — a small statistical adjustment was applied since 9 months, while solid, isn't yet a long history. Overall this reflects strong income stability."*
- *"94% of your 14 recorded payments were made on or before the due date, contributing a smoothed score of 88/100."*
- *"Your earnings show an upward trend of about 2.5% per month over the last 9 months. Seasonal adjustment was not applied because at least 12 months of history is needed."*
- *"Your platform tenure is 9 months."*
- *"Your score is based on 9 months of earnings data, 14 payment records, a complete profile, and 2 income sources — giving this score High confidence."*

Note that the shrinkage steps visibly pull an already-strong worker's numbers down slightly across all three statistical factors — this is the system being appropriately cautious about a still-moderate (9-month) history, and is itself a strong "we're not overclaiming" point for judges.

## 15. Final Pseudocode

```
function computeCrediBridgeScore(worker):

    WEIGHTS_PCT = { income: 33, payment: 28, trend: 22, tenure: 17 }
    CV_BREAKPOINTS    = [(0.00,100),(0.15,90),(0.30,75),(0.50,55),(0.80,30),(1.20,10)]
    TREND_BREAKPOINTS = [(-8,10),(-3,35),(-1,60),(0,70),(3,100)]
    PRIOR = 70

    factors = {}

    # --- Income Consistency ---
    months = length(worker.earnings)
    if months < 2:
        factors.income = EXCLUDED
    else:
        med = median(worker.earnings)
        mad = median([abs(e - med) for e in worker.earnings])
        cv  = mad / med if med > 0 else 0
        raw = interpolate(cv, CV_BREAKPOINTS, clampLow=100, clampHigh=10)
        shrunk = (months*raw + 3*PRIOR) / (months+3)
        factors.income = { value: shrunk, n: months, raw: raw, cv: cv }

    # --- Payment Regularity ---
    records = [r for r in worker.payments if r.due_date and r.paid_date]
    n = length(records)
    if n == 0:
        factors.payment = EXCLUDED
    else:
        pts = []
        for r in records:
            d = daysBetween(r.paid_date, r.due_date)
            if d <= 0: pts.append(100)
            elif d <= 5: pts.append(85)
            elif d <= 15: pts.append(50)
            elif r.unpaid_flag: pts.append(0)
            else: pts.append(15)
        raw = average(pts)
        on_time_pct = 100 * count(r in records where daysBetween(r.paid_date,r.due_date) <= 0) / n
        shrunk = (n*raw + 5*PRIOR) / (n+5)
        factors.payment = { value: shrunk, n: n, raw: raw, on_time_pct: on_time_pct }

    # --- Earnings Trend ---
    if months < 2:
        factors.trend = EXCLUDED
    else:
        series = worker.earnings   # chronological
        seasonal_adjusted = false
        if months >= 12:
            series = deseasonalize_ratio_to_moving_average(series)
            seasonal_adjusted = true
        slope = theilSenMedianSlope(series)
        norm_slope_pct = 100 * slope / median(series)
        raw = interpolate(norm_slope_pct, TREND_BREAKPOINTS, clampLow=10, clampHigh=100)
        shrunk = (months*raw + 3*PRIOR) / (months+3)
        factors.trend = { value: shrunk, n: months, raw: raw, slope_pct: norm_slope_pct,
                           seasonal_adjusted: seasonal_adjusted }

    # --- Platform Tenure ---
    if worker.tenure_start_date is null:
        factors.tenure = EXCLUDED
    else:
        m = monthsSince(worker.tenure_start_date)
        value = min(100 * ln(1+m) / ln(1+36), 100)
        factors.tenure = { value: value, months: m }

    # --- Redistribution & minimum threshold ---
    included = [f for f in factors if factors[f] != EXCLUDED]
    if length(included) < 2:
        return { status: "INSUFFICIENT_DATA" }

    total_w = sum(WEIGHTS_PCT[f] for f in included)
    raw_score_900 = sum(
        (factors[f].value / 100) * (WEIGHTS_PCT[f] / total_w) * 900
        for f in included
    )

    # --- Confidence ---
    earn_cov = (min(months_or_0/6,1)*100) if income not excluded else 0
    pay_cov  = (min(n_or_0/10,1)*100)     if payment not excluded else 0
    profile_pct = worker.filled_required_fields / worker.total_required_fields * 100
    diversity   = min(worker.distinct_sources/3,1)*100
    validity    = worker.valid_records / worker.total_records * 100

    confidence_score = 0.30*earn_cov + 0.30*pay_cov + 0.20*profile_pct
                      + 0.10*diversity + 0.10*validity

    if confidence_score >= 75:  tier, cap = "HIGH", 900
    elif confidence_score >= 40: tier, cap = "MEDIUM", 820
    else:                        tier, cap = "LOW", 650

    displayed_score = round(min(raw_score_900, cap))
    band = lookupBand(displayed_score)   # per Section 8 table

    return {
        score: displayed_score,
        band: band,
        confidence_tier: tier,
        confidence_score: confidence_score,
        factors: factors,
        explanations: generateExplanations(factors, tier)   # fixed templates, Section 9
    }
```

**Helper functions referenced above** (`interpolate`, `theilSenMedianSlope`, `deseasonalize_ratio_to_moving_average`, `daysBetween`, `monthsSince`, `lookupBand`, `generateExplanations`) are all fully specified by the formulas and tables in Sections 4, 6, 8, and 9 respectively — no additional assumptions are required to implement them.
